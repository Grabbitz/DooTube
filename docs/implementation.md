# DooTube implementation

The original [architecture proposal](architecture.md) and [design brief](design-brief.md) remain design history. This document describes the current Watch implementation; verification results are recorded separately in [Verification](verification.md).

## Native chrome and official media surface

The executable is `dootube`, written in Rust using `objc2`, `objc2-app-kit`, `objc2-foundation`, and `objc2-web-kit`. AppKit owns the macOS application, window, native bar (`src/cinema_bar.rs`), queue drawer, menus, and notices. Two persistent `WKWebView`s retain the official YouTube and YouTube Music websites (`src/web.rs`). There is no Electron runtime, local web server, bundled home page, unofficial media extractor, or custom video decoder.

A document-start user script hides only the site header the native bar replaces: YouTube's masthead and the guide drawer's duplicate logo header (`src/youtube_chrome.css`) and YouTube Music's nav bar (`src/music_chrome.css`). The sites' own guides (Home, Shorts, Subscriptions, You; Home, Explore, Library) stay. It does not touch the players, player controls, branding inside the players, ads, captions, lyrics, or page content. The same script reports audible media and Picture in Picture state. Provider web views retain their Safari application-name suffix. The window explicitly uses Dark Aqua; the native bar is clear over a backdrop that matches the page, and the drawer uses a near-YouTube dark gray.

## Sections, playback, and sign-in

YouTube and YouTube Music each retain their own web view, page, history, and playback position. Command-1/2 and the section buttons show that section's provider page, opening its home the first time; the brand button and View → Home load the section's provider home. Returning to a current player does not reload its page. Cross-provider links open in their own section. When media becomes audible in one section, the app pauses the other; a background section keeps playing until the other makes sound, as before. YouTube Music's track/window metadata comes from the page's Media Session metadata.

A document-start script on `music.youtube.com` (`src/music_player.js`) reports the official player bar's track, artist, largest artwork URL, and play state. The Up Next drawer shows the native Now Playing card while the YouTube section is selected. Artwork opens the retained Music provider directly, not Music Home. The card's Previous, Play/Pause, and Next, the Controls menu, and the Dock menu press the site's own buttons; there is no separate player. Next/Previous step aside while editing text. Artwork remains restricted to HTTPS Google image hosts and is kept in memory.

The two provider web views share the default website data store, so signing in applies to both. The native account menu and the DooTube menu load Google's official sign-in page (`accounts.google.com/ServiceLogin` for the `youtube` service, continuing to the current section) inside the app. Main-frame sign-in navigation uses the exact allowlist from Google's supported_domains, fetched 2026-10-24, src/google_domains.rs; this list must be refreshed by hand. Account hosts use `accounts.<domain>` and `/accounts/` redirects use `<domain>` or `www.<domain>`, with no suffix matching. Navigation is HTTPS-only and excludes credentials and ports. The document-start passkey script is generated from the same domains and exact-host constants. The `WKUIDelegate` loads allowed YouTube and sign-in popups in the same web view; other user-activated HTTP(S) popups are handed to the browser, and other popup requests show a notice. If a main-frame hop is blocked while the pane is on a sign-in page, DooTube shows a sticky notice containing only the blocked host and path (never query or fragment). These pages cannot be typed in. DooTube never reads or stores credentials: it only checks whether YouTube's `LOGIN_INFO`/`SAPISID` cookies exist to show the signed-in state, and refreshes the other section when that state changes. Sign Out loads YouTube's own `/logout` in the YouTube section. Google decides whether it accepts an embedded sign-in; the regional completion-hop explanation remains a hypothesis until retried by the user.

Passkeys cannot work here: the system authorizes WebAuthn in a `WKWebView` only for apps with Apple's restricted `com.apple.developer.web-browser.public-key-credential` entitlement or the site's associated domains, and rejects every other request. Google's page still detects `PublicKeyCredential`, offers a passkey, and ends on a "check Bluetooth" error. A document-start script in all frames (`web::sign_in_passkey_script`) removes `PublicKeyCredential` and rejects `publicKey` credential requests with `NotAllowedError` only on the sign-in hosts described above. It embeds the domains and exact hosts from shared Rust constants; YouTube pages keep WebKit's defaults. This mirrors Kaset's [ADR-0033](https://github.com/sozercan/kaset/blob/main/docs/adr/0033-login-passkey-suppression.md). Accounts that allow only passkeys cannot sign in.

## Full screen, Picture in Picture, and video formats

Video full screen is DooTube's own, not WebKit's element full screen (disabled). An injected shim implements `requestFullscreen`/`exitFullscreen` and the fullscreen properties and events, so YouTube's F key, button, and full-screen UI work unchanged. On a request the app snapshots the page to stand in for it, moves the web view at full size onto a borderless screen-sized stage window (invisible until the page has painted its fullscreen layout), then zooms by animating only a layer transform from the player's rect while a black backdrop fades in; WebKit never relayouts mid-animation. Exit reverses the zoom, snapshots the video's current frame, returns the web view to its container under the page snapshot with that frame laid over the player, and removes both once the page has repainted, so the player doesn't flash back to the frame from when full screen began. WebKit paints snapshots in the page's process, stalling YouTube while it does, so both are taken at standard rather than Retina resolution: with a 60 fps video a Retina page snapshot took about 0.5 s, a standard one about 0.1 s (F to zoom start went from about 0.73 s to 0.3 s), and the exit frame adds about 0.05 s. The Dock and menu bar are hidden while the stage is up, except when the window is already in native full screen. Switching sections, minimizing, closing, a page load, or the page's web process ending ends video full screen immediately.

When WebKit ends a section's web process (a crash, or macOS reclaiming memory), the section reloads its current page on its own, keeping its history; a section in the background reloads when it is next shown. If the same section's process ends again within a minute, it shows "A Problem Repeatedly Occurred" with Try Again instead of reloading in a loop. Picture in Picture from that section ends with the process.

Control-Command-F and the green window button use AppKit's native window full screen. The native bar sits in the window's unified titlebar row (an empty `NSToolbar` sizes it) beside the traffic lights, rather than in toolbar items; Control-Command-S toggles the Up Next drawer. A separate transient frame-autosave name preserves the normal window frame. Video fullscreen still uses the separate borderless stage described above, without the queue covering its controls.

Picture in Picture uses the standard web API on the playing (or first loaded) video of the section where PiP is active, else the current section; it is offered from the native bar's PiP button and View → Picture in Picture. Every outcome is reported: no video, an unstarted video, a video that disallows PiP, a script error, or a rejected request (for example `NotAllowedError` when WebKit does not treat the command as a user gesture) each show a notice instead of doing nothing. A section with a video in Picture in Picture is exempt from the pause/suspend on hide, minimize, or close, because the video stays visible in its floating window.

### Video formats

DooTube adds no decoder and does not choose streams: YouTube offers resolutions, frame rates, and HDR based on what this WebKit reports it can decode and on the display, and the viewer picks in the player's settings. Measured inside DooTube on the verification Mac (macOS 27.0.1, 1512×982 points at 2×, HDR-capable display): Media Source Extensions accept H.264, VP9, VP9 Profile 2 10-bit HDR, and Opus; they reject AV1 (8-bit and 10-bit). `dynamic-range: high` matched; Picture in Picture and element full screen are enabled. YouTube 8K streams exist in VP9 and AV1, so 8K availability depends on YouTube offering a VP9 8K stream for a given video; AV1-only streams are not available on this Mac. "IMAX" is not a separate YouTube stream format: such videos play at whatever aspect ratio and quality YouTube serves.

## Navigation and Up Next

Search text is turned into an official search URL for the current section (YouTube results or YouTube Music search). Supported YouTube page/video links open in their section's web view. Video links, including their playlist/time query parameters, remain web URLs; YouTube supplies player controls and media behavior. The app's URL parsing is not a YouTube catalog API or a guarantee that a supplied video exists or is playable.

Up Next is app-owned saved video URLs with the title captured when it was saved, not YouTube's queue; it is shared by both sections and each entry opens in the section its link belongs to. Opening an entry is manual: there is no auto-next promise and no restored video autoplay on launch. A saved YouTube video resumes where it was left: on `youtube.com/watch` pages the document-start script reports the main player's (`#movie_player`) position every 15 s while it plays and on pause, end, `yt-navigate-start`, and `pagehide`, skipping ads (`ad-showing`); if that video is in Up Next its position is stored with it (quietly: no sidebar reload, and a failed write is dropped rather than shown, since it repeats). Positions under 10 s or within 20 s of the end clear it. Opening the entry adds `t=<seconds>s` (replacing `t`/`start`) to watch and `youtu.be` links; Music, Shorts, and live links open as saved. Whether YouTube honors `t` in every case has not been tested. Search results and ordinary page links are not queue entries. Entries are matched by video ID, so the same video in another link form (`youtu.be`, `music.youtube.com`, extra `t`/`list` parameters) is not added twice. YouTube titles are only taken once YouTube has updated the document title for that video; an entry saved without one shows its video ID and gains its title the next time that video is open.

No-argument launch opens YouTube's own home page in the YouTube section. A startup search/link opens its official provider directly.

The native bar is one 52-point row: Back/Forward, the brand (provider home), and the YouTube/Music sections on the left; search centered; Save, PiP, the Up Next count, and the account menu on the right. Save is disabled away from a video. On reveal, a provider still attached to the main container is sized to its current bounds; a provider moved to the fullscreen stage retains the stage's geometry.

Up Next opens as a 340-point native drawer with a scrim, Close button, and Escape equivalent. Control-Command-S and the bar's Up Next button use the same drawer. The existing native table keeps thumbnail caching, row selection, click-to-open, drag reorder, drag-out URLs, context menus, and keyboard menu commands; the drawer starts closed. Saved rows are taller and no longer share the list with provider destinations. Window geometry is restored, but the old split-view/sidebar-width preference is no longer used. Notices retain their existing persistence and dismissal behavior.
When signed in, the Cinema bar shows the account photo (an HTTPS URL on Google's avatar hosts from the same response, downloaded once and kept in memory), and the native account menu header shows the display name with the email, or the @handle if there is no email, as its subtitle (macOS 14.4+). The Cinema bar's account control has a tooltip with the name and email, or the handle if no email is available; a name-only identity is valid. The `/getAccountSwitcherEndpoint` response is fetched from `www.youtube.com` with the loaded page's own same-origin session; the active account is identified only by an explicitly selected account item, and its email is taken from its enclosing account section. Identity is held in memory only and cleared on sign-out or when starting account sign-in/switching; if lookup fails, the menu shows “Signed in to YouTube.”

A new provider destination, search, or link request clears the pane's previous network/process-failure flags before loading. If no page has committed, the placeholder returns to Loading while that request is pending; another error restores Try Again. An already committed page remains visible during navigation.

Typed URLs are restricted to supported YouTube hosts (including `music.youtube.com`), without embedded credentials or custom ports; HTTP input is upgraded to HTTPS. Top-level automatic off-site navigation is blocked except the Google sign-in hosts above, while a user-activated ordinary external web link is handed to the system browser. The app requests user interaction before media playback, explicitly pauses media, and suspends WebKit playback in both sections when hidden, minimized, or closed, except a section with a video in Picture in Picture. Showing the window again lifts suspension only when the window is visible and open; it does not issue an automatic play command. These are implementation behaviors, not a claim that lifecycle/playback interaction was exercised in this session.

## State and data boundaries

Saved Up Next state lives in `~/Library/Application Support/DooTube/state.json`. Writes use a sibling temporary file and rename. Unreadable saved state is reported rather than silently replaced; queue editing is blocked while the saved state cannot be loaded. A save failure is reported in the app and must not be interpreted as durable persistence.

The app does not import another browser's cookies, history, or account data. The official sites have their own WebKit-managed website data; sign-in state lives there, not in DooTube's state file. DooTube does not implement Google OAuth.

Native Music catalog/lyrics/credits, EQ/audio capture, a custom player, background audio beyond Picture in Picture, downloads, and an unofficial provider adapter are not shipped here. YouTube Music is its official website, including its own Lyrics tab. An EQ inside the page is not possible: routing YouTube Music's media element through Web Audio in this web view produced only silence (and silenced the song), so EQ would need the Core Audio process-tap route and policy review in [Architecture](architecture.md). API availability, provider policy, and future design goals in the earlier documents are not runtime evidence.

## Local bundle

`scripts/build-app.sh` builds with the lockfile, packages the binary at `DooTube.app/Contents/MacOS/dootube`, copies bundle metadata and the icon (removing a `Contents/Resources/cinema` left by 0.3.0 builds), derives the displayed version from Cargo metadata, and ad-hoc signs the complete bundle. `scripts/run.sh` opens that exact bundle through Launch Services. `scripts/install.sh --open` replaces only `/Applications/DooTube.app`; the queue path, bundle identifier, and provider website data store remain unchanged.

The bundle identifier is provisionally `com.dootube.app`. Both `MACOSX_DEPLOYMENT_TARGET` and `LSMinimumSystemVersion` are 14.2. High-resolution rendering is enabled. No camera, microphone, screen/audio capture usage descriptions, entitlements, or App Transport Security exceptions are added. This is a host-architecture development bundle, not a notarized distribution artifact or a runtime compatibility certification for macOS 14.2.
