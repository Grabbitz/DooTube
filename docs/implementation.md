# Native Watch implementation

The original [architecture proposal](architecture.md) and [design brief](design-brief.md) remain design history. This document describes the current Watch implementation; verification results are recorded separately in [Verification](verification.md).

## Native chrome and official media surface

The executable is `dootube`, written in Rust using `objc2`, `objc2-app-kit`, `objc2-foundation`, and `objc2-web-kit`. AppKit owns the macOS application, a full-size-content window with a unified `NSToolbar`, an `NSSplitViewController` source-list sidebar, menus, and notices. Two visible `WKWebView`s host the official YouTube and YouTube Music websites (`src/web.rs`); only the active section's view is shown. There is no Electron runtime, local web server, unofficial media extractor, custom video decoder, or hidden audio player.

A document-start user script hides only the site navigation the native toolbar and sidebar replace: YouTube's masthead, mini guide, and guide drawer (`src/youtube_chrome.css`) and YouTube Music's nav bar and guide (`src/music_chrome.css`). It does not touch the players, player controls, branding inside the players, ads, captions, lyrics, or page content. The same script reports to the app when a media element becomes audible (unmuted and playing) and when a video enters or leaves Picture in Picture. The web views append a `Version/27.0 Safari/605.1.15` application name to WebKit's default user agent; with it, YouTube follows the system light/dark appearance instead of serving its light theme to an unrecognized browser.

## Sections, playback, and sign-in

YouTube and YouTube Music each have their own web view, so switching sections keeps each page, history, and playback position. A section is opened (at its Home) the first time it is shown. Links to `music.youtube.com` clicked or redirected inside the YouTube section open in the Music section; links to YouTube clicked inside Music open in the YouTube section. When media becomes audible in one section, the app pauses all media in the other, so only one section plays at a time; a section left in the background keeps playing until the other makes sound. YouTube Music keeps its document title fixed, so its window title and saved-song titles come from the page's Media Session metadata.

Both web views share the default website data store, so signing in applies to both. The account toolbar menu and the DooTube menu load Google's official sign-in page (`accounts.google.com/ServiceLogin` for the `youtube` service, continuing to the current section) inside the app. Main-frame sign-in navigation uses the exact allowlist from Google's supported_domains, fetched 2026-10-24, src/google_domains.rs; this list must be refreshed by hand. Account hosts use `accounts.<domain>` and `/accounts/` redirects use `<domain>` or `www.<domain>`, with no suffix matching. Navigation is HTTPS-only and excludes credentials and ports. The document-start passkey script is generated from the same domains and exact-host constants. The `WKUIDelegate` loads allowed YouTube and sign-in popups in the same web view; other user-activated HTTP(S) popups are handed to the browser, and other popup requests show a notice. If a main-frame hop is blocked while the pane is on a sign-in page, DooTube shows a sticky notice containing only the blocked host and path (never query or fragment). These pages cannot be typed in. DooTube never reads or stores credentials: it only checks whether YouTube's `LOGIN_INFO`/`SAPISID` cookies exist to show the signed-in state, and refreshes the other section when that state changes. Sign Out loads YouTube's own `/logout` in the YouTube section. Google decides whether it accepts an embedded sign-in; the regional completion-hop explanation remains a hypothesis until retried by the user.

Passkeys cannot work here: the system authorizes WebAuthn in a `WKWebView` only for apps with Apple's restricted `com.apple.developer.web-browser.public-key-credential` entitlement or the site's associated domains, and rejects every other request. Google's page still detects `PublicKeyCredential`, offers a passkey, and ends on a "check Bluetooth" error. A document-start script in all frames (`web::sign_in_passkey_script`) removes `PublicKeyCredential` and rejects `publicKey` credential requests with `NotAllowedError` only on the sign-in hosts described above. It embeds the domains and exact hosts from shared Rust constants; YouTube pages keep WebKit's defaults. This mirrors Kaset's [ADR-0033](https://github.com/sozercan/kaset/blob/main/docs/adr/0033-login-passkey-suppression.md). Accounts that allow only passkeys cannot sign in.

## Full screen, Picture in Picture, and video formats

Video full screen is DooTube's own, not WebKit's element full screen (disabled). An injected shim implements `requestFullscreen`/`exitFullscreen` and the fullscreen properties and events, so YouTube's F key, button, and full-screen UI work unchanged. On a request the app snapshots the page to stand in for it, moves the web view at full size onto a borderless screen-sized stage window (invisible until the page has painted its fullscreen layout), then zooms by animating only a layer transform from the player's rect while a black backdrop fades in; WebKit never relayouts mid-animation. Exit reverses the zoom, returns the web view to its container under the snapshot, and removes the snapshot once the page has repainted. The Dock and menu bar are hidden while the stage is up, except when the window is already in native full screen. Switching sections, minimizing, closing, or a page load ends video full screen immediately.

Control-Command-F and the green window button use AppKit's native window full screen. AppKit auto-hides the menu bar and toolbar, sliding the toolbar back into view with the menu bar on hover; the sidebar remains in place and stays user-toggleable with Control-Command-S. A separate transient frame-autosave name is used during fullscreen, preserving the saved normal window frame across launches. Failed entry restores the normal autosave name; failed exit restores the fullscreen autosave name. Neither native window fullscreen path changes the official player DOM or overlays its controls.

Picture in Picture uses the standard web API on the playing (or first loaded) video of the section where PiP is active, else the current section; it is offered from a toolbar button and View → Picture in Picture. Every outcome is reported: no video, an unstarted video, a video that disallows PiP, a script error, or a rejected request (for example `NotAllowedError` when WebKit does not treat the command as a user gesture) each show a notice instead of doing nothing. A section with a video in Picture in Picture is exempt from the pause/suspend on hide, minimize, or close, because the video stays visible in its floating window.

### Video formats

DooTube adds no decoder and does not choose streams: YouTube offers resolutions, frame rates, and HDR based on what this WebKit reports it can decode and on the display, and the viewer picks in the player's settings. Measured inside DooTube on the verification Mac (macOS 27.0.1, 1512×982 points at 2×, HDR-capable display): Media Source Extensions accept H.264, VP9, VP9 Profile 2 10-bit HDR, and Opus; they reject AV1 (8-bit and 10-bit). `dynamic-range: high` matched; Picture in Picture and element full screen are enabled. YouTube 8K streams exist in VP9 and AV1, so 8K availability depends on YouTube offering a VP9 8K stream for a given video; AV1-only streams are not available on this Mac. "IMAX" is not a separate YouTube stream format: such videos play at whatever aspect ratio and quality YouTube serves.

## Toolbar, sidebar, and Up Next

Search text is turned into an official search URL for the current section (YouTube results or YouTube Music search). Supported YouTube page/video links open in their section's web view. Video links, including their playlist/time query parameters, remain web URLs; YouTube supplies player controls and media behavior. The app's URL parsing is not a YouTube catalog API or a guarantee that a supplied video exists or is playable.

Up Next is app-owned saved video URLs with the title captured when it was saved, not YouTube's queue; it is shared by both sections and each entry opens in the section its link belongs to. Opening an entry is manual: there is no auto-next promise, no restored playback position, and no restored video autoplay on launch. Search results and ordinary page links are not queue entries. Entries are matched by video ID, so the same video in another link form (`youtu.be`, `music.youtube.com`, extra `t`/`list` parameters) is not added twice. YouTube titles are only taken once YouTube has updated the document title for that video; an entry saved without one shows its video ID and gains its title the next time that video is open.

The app opens YouTube Home at launch (or the startup search/link in its section) behind a spinner until the first page commits; a failed first load shows a centered Try Again state. The toolbar holds the sidebar toggle, Back/Forward for the current section (enabled from WebKit history), the centered YouTube | Music switch, the search field, Picture in Picture, Save to Up Next (enabled only on an unsaved video page; a checkmark once saved), and the account menu. The sidebar lists the current section's destinations (YouTube: Home, Shorts, Subscriptions, History; Music: Home, Explore, Library) and Up Next; the row matching the current page stays selected. Saved rows support click to open, a context menu (Open, Move Up, Move Down, Remove from Up Next), and the Up Next menu commands, which act on the selected row only while the sidebar has keyboard focus so Command-Delete keeps its text-editing meaning elsewhere. Navigation notices and errors appear as a dismissible bubble at the bottom of the page and hide after five seconds; save and unreadable-queue errors stay until dismissed. The window frame and sidebar width are restored between launches.
When signed in, the toolbar shows the account photo (an HTTPS URL on Google's avatar hosts from the same response, downloaded once and kept in memory), and the menu header shows the display name with the email, or the @handle if there is no email, as its subtitle (macOS 14.4+). The toolbar tooltip shows the name with the email, or the handle if no email is available; a name-only identity is valid. The `/getAccountSwitcherEndpoint` response is fetched from `www.youtube.com` with the loaded page's own same-origin session; the active account is identified only by an explicitly selected account item, and its email is taken from its enclosing account section. Identity is held in memory only and cleared on sign-out or when starting account sign-in/switching; if lookup fails, the menu shows “Signed in to YouTube.”


Typed URLs are restricted to supported YouTube hosts (including `music.youtube.com`), without embedded credentials or custom ports; HTTP input is upgraded to HTTPS. Top-level automatic off-site navigation is blocked except the Google sign-in hosts above, while a user-activated ordinary external web link is handed to the system browser. The app requests user interaction before media playback, explicitly pauses media, and suspends WebKit playback in both sections when hidden, minimized, or closed, except a section with a video in Picture in Picture. Showing the window again lifts suspension only when the window is visible and open; it does not issue an automatic play command. These are implementation behaviors, not a claim that lifecycle/playback interaction was exercised in this session.

## State and data boundaries

Saved Up Next state lives in `~/Library/Application Support/DooTube/state.json`. Writes use a sibling temporary file and rename. Unreadable saved state is reported rather than silently replaced; queue editing is blocked while the saved state cannot be loaded. A save failure is reported in the app and must not be interpreted as durable persistence.

The app does not import another browser's cookies, history, or account data. The official sites have their own WebKit-managed website data; sign-in state lives there, not in DooTube's state file. DooTube does not implement Google OAuth.

Native Music catalog/lyrics/credits, EQ/audio capture, custom transport controls, background audio beyond Picture in Picture, downloads, and an unofficial provider adapter are not shipped here. YouTube Music is its official website. API availability, provider policy, and future design goals in the earlier documents are not runtime evidence.

## Local bundle

`scripts/build-app.sh` builds with the lockfile, packages the compiled binary at `DooTube.app/Contents/MacOS/dootube`, copies native bundle metadata, derives the displayed version from Cargo metadata, and ad-hoc signs the local bundle. `scripts/run.sh` opens that exact bundle through Launch Services without forcing a second instance.

The bundle identifier is provisionally `com.dootube.app`. Both `MACOSX_DEPLOYMENT_TARGET` and `LSMinimumSystemVersion` are 14.2. High-resolution rendering is enabled. No camera, microphone, screen/audio capture usage descriptions, entitlements, or App Transport Security exceptions are added. This is a host-architecture development bundle, not a notarized distribution artifact or a runtime compatibility certification for macOS 14.2.
